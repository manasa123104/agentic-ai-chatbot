What is BA (Business Analyst)?

The Business Analyst translates a business requirement (for example, “transfer money between accounts”) into structured user stories for the selected domain, each with Given / When / Then acceptance criteria.

Role
Stage 1. Acts as a senior business analyst: it identifies the users, their goals, and the evidence that a story is complete.
Input
A requirement you enter, or existing story files (.md, .txt, .docx, .csv, .feature, a folder or a ZIP), or stories imported from a GitHub repository. Limits: 55,000 characters in the input field, 5 MB per file, 1,000 files or 100 MB per ZIP.
Output
User stories with Given / When / Then acceptance criteria. You may edit or download them, pass them through unchanged, or request a refinement that preserves every story.
Next stage
The stories become the input to the Developer. Use “Send to next stage”, or run all stages to pass them forward automatically.

What is Developer?

The Developer reads the user stories and produces commented, working source code in the selected language (Java, Python, JavaScript, C#, Go and others).

Role
Stage 2. Acts as a senior engineer for the chosen domain and language, following the stories and any approved training examples.
Input
User stories from the Business Analyst, or stories you paste directly.
Output
Source files with comments. You may edit the code, download a file, the stage ZIP or a business-logic summary, or push it to GitHub.
Next stage
The code proceeds to the Tester. The Deploy stage uses the same implementation.

What is Tester?

The Tester verifies that the Developer’s implementation behaves as specified. It can produce any combination of three test types:

  • Unit tests – automated checks of individual functions or classes.
  • Automation (Selenium) – browser scripts that exercise the application as an end user would.
  • Manual / functional testing – step-by-step cases (preconditions, steps, expected result) for a person to execute against the running application.
Role
Stage 3. Acts as a tester who demonstrates that the stories were implemented correctly.
Input
The Developer’s code, together with the run’s user stories for automation and manual cases.
Output
Test files in three tabs (unit, automation, manual). Select which types to generate from the list above the results, then download them as files or a ZIP archive.
Next stage
When the tests are acceptable, the Data Analyst produces KPIs and charts, then Deploy packages the code.

What is Data Analyst?

The Data Analyst produces graphs and statistics for the run: key performance indicators, a Chart.js dashboard and a metrics JSON file. Open dashboard.html — each chart includes a high-level overview and an analysis of the figures.

Role
Stage 4. Acts as a data analyst for the selected domain. The dashboard presents nine charts (operations and quality), each with a description and an analysis, together with a KPI summary.
Input
The Developer’s code, and the run’s stories and tests when they are available.
Output
analytics/STATS.md (written analysis), analytics/dashboard.html (interactive charts with descriptions) and analytics/metrics.json. Download them from this card or open the HTML file in a browser.
Next stage
The Deploy stage prepares the same Developer code for release.

What is Deploy?

Deploy prepares the implementation so the application can be packaged and released. It generates the files only; it does not publish or start the application.

Role
Stage 5. Acts as a DevOps engineer for the selected language: it writes the artefacts required to build and run the application in a typical environment.
Input
The Developer’s code.
Output
A Dockerfile, build scripts, a GitHub Actions CI/CD workflow, Kubernetes YAML, docker-compose and a DEPLOY.md guide. Download them from the Deploy card as a file or a ZIP archive. You may also select “Build image locally” when Docker is installed.
Next stage
The Trainer reviews the completed run and stores the outputs you approve.

What is Trainer?

The Trainer is BOT’s memory. It does not generate or deploy artefacts; it retains the outputs you approve so later runs in the same domain and language improve.

Role
Stage 6, the final stage. Reviews the run and stores approved (and corrected) outputs as few-shot examples.
Input
The run: Business Analyst stories, Developer code, Tester cases, Data Analyst charts and Deploy files. Select the stages to store. Edits you make in an output field are saved as corrected, and you may add feedback such as “always include an AML screening story”.
Output
A training report, with examples stored in data/bot-training.json on the machine that runs BOT. On the public hosted site that file is temporary and is cleared on restart or redeploy, so treat training there as a demonstration. Nothing is stored automatically: use Save this run as training.
Next stage
The pipeline is complete. Stored examples are provided to the model the next time you run a stage for the same domain. An All 6 stages done — Push to GitHub panel at the end of the page lets you push the full run to a new GitHub branch and obtain a link.

What is Business Analyst?

The Business Analyst turns a plain requirement (for example “transfer money between accounts”) into clear user stories for the domain you picked, each with acceptance criteria written as Given / When / Then.

You can type the requirement, upload story files (or a ZIP or folder), or pull existing stories from a GitHub repository. The stories become the input for the Developer.

What is Developer?

The Developer reads the user stories and writes working, commented code that implements them, in the language you chose (Java, Python, JavaScript, C#, Go and many more).

Edit the code if you like, download it, or push it to GitHub. The Tester, Data Analyst and Deploy stages build on this code.

What is Data Analyst?

The Data Analyst turns this run into graphs and statistics: a KPI summary (STATS.md), a Chart.js dashboard.html you can open in a browser, and metrics.json for the chart data.

Open the dashboard to see nine charts in two groups. Each one has a title, a High-level overview note, and an Analysis box that interprets the numbers for this domain:

  • Weekly volume — demand across the week (transfers, appointments, shipments or requests).
  • Success rate — how much of that demand completed on the happy path.
  • Daily outcomes — the same volume split into completed vs unsuccessful.
  • Channel mix — which channel raised the work (app, web, branch, API…).
  • Cycle / wait / transit time — how long the work takes each day.
  • Test mix — unit vs automation vs manual coverage from the Tester stage.
  • Quality snapshot — estimated defects vs how many are still open.
  • Failure reasons — why items left the happy path.
  • Defect severity — critical / major / minor / info split of estimated defects.

Figures are illustrative, domain-flavoured metrics derived from the stories, code and tests in the run — not a live database. Deploy still uses the Developer’s code next.

Deploy prepares the code so the app can be packaged and released. It writes a Dockerfile, build scripts, a CI/CD workflow (GitHub Actions), Kubernetes YAML, docker-compose and a DEPLOY.md guide that explains how to run it.

It only produces the files; download them from this card. The Trainer comes next.

What is Tester?

The Tester checks that the Developer's code works. There are three kinds of test, and you can ask for any of them or all:

  • Unit tests – automated checks of small pieces of the code (one function or class at a time).
  • Automation (Selenium) – scripts that open a real browser and click through the app like a robot user.
  • Manual / Functional testing – step-by-step test cases (preconditions, steps, expected result) that a person runs by hand against the running app.

Pick the mode in the drop-down above the results. Everything it writes can be downloaded as files or a ZIP.

    What is Trainer?

    The Trainer is BOT's memory. It does not write or deploy anything itself: it keeps the outputs you approve so the next runs in the same domain (and language) come out better.

    • What it learns from – outputs you press Approve for training on, or tick and save here: Business Analyst stories, Developer code, Tester cases (unit, automation, manual) and Deploy files. Your own corrections to an output are saved as you edited them.
    • How it helps – saved examples are shown to the model as “this is what a good answer looks like” the next time you run that stage for the same domain.
    • Where it is kept – in data/bot-training.json on the machine running BOT. On the public Render site that file is temporary and is wiped on restart or redeploy, so treat training there as a demo.
    • Nothing is saved automatically – press Save this run as training when you are happy with the results.

    When the Trainer finishes, the whole pipeline is complete: the All 6 stages done — Push to GitHub panel appears at the very end of this page, so you can push everything this run generated to a new GitHub branch and get a new link.
